        q: "Explain Kafka's core architecture — brokers, topics, partitions, consumer groups, and offsets.",
        a: `Kafka is a distributed event streaming platform. Think of it as a highly durable, high-throughput message queue.

Core components:

Broker: A Kafka server. Messages are stored on brokers. A Kafka cluster has multiple brokers for redundancy.

Topic: A named channel where messages are published. Like a table in a DB but for events. I have topics like book-request-events, notification-events.

Partition: Each topic is split into partitions — ordered, immutable sequences of messages. Partitions allow parallel processing and horizontal scaling. If I have 3 partitions, up to 3 consumers can process simultaneously.

Offset: A number that identifies a message's position in a partition. Consumer tracks which offset it has processed. If consumer crashes, it resumes from the last committed offset — no messages lost.

Producer: Publishes messages to a topic. My Request Service is a producer — it publishes "RequestApproved" events.

Consumer Group: A group of consumers that collectively read from a topic. Each partition is assigned to exactly one consumer in the group. My Notification Service has a consumer group "notification-group".

How I used it:
  Request Service (Producer) → [book-request-events topic, 3 partitions] → Notification Service (Consumer Group, 3 instances)
  Each Notification Service instance handles one partition. If I scale to 3 instances, I get 3x throughput. Sub-100ms processing latency because Kafka is in-memory and the consumer is always running.`

        a: `Both are message brokers but with different design philosophies.

RabbitMQ:
- Traditional message queue (push-based). Broker pushes messages to consumers.
- Messages are deleted after consumption (by default).
- Better for complex routing patterns (exchanges, bindings, routing keys).
- Easier to set up for simple use cases.

        q: "Explain Kubernetes liveness and readiness probes. How did you configure them?",
        a: `Kubernetes probes are health checks that Kubernetes runs to determine if a pod is alive and ready to serve traffic.

Liveness Probe: "Is this container still running correctly? Should it be restarted?"
- If liveness probe fails repeatedly, Kubernetes KILLS and RESTARTS the pod.
- Use case: Detect deadlocks, frozen processes, infinite loops — app is running but stuck.

Readiness Probe: "Is this container ready to receive traffic?"
- If readiness probe fails, Kubernetes removes the pod from the Service's endpoint list — no traffic is sent to it. Pod is NOT restarted.
- Use case: App is starting up (loading cache, connecting to DB). Pod is alive but not ready yet.

      port: 8080

    periodSeconds: 15           # Check every 15 seconds
    failureThreshold: 3         # Restart after 3 consecutive failures

  readinessProbe:
    httpGet:
      path: /actuator/health/readiness
      port: 8080
    initialDelaySeconds: 30
    periodSeconds: 10
    failureThreshold: 3

Spring Boot Actuator exposes two separate endpoints:
- /actuator/health/liveness: Returns UP if app JVM is running (simple check).
- /actuator/health/readiness: Returns UP only when app is fully ready — DB connected, Redis connected, Kafka consumer started, cache warmed up.

Real scenario: During a rolling update of Book Service, new pods become "alive" (liveness UP) in 30 seconds but "ready" (readiness UP) in 60 seconds after cache warming. Kubernetes only sends traffic after readiness is UP — zero user impact during deployments.`

        q: "Explain React's virtual DOM and reconciliation algorithm.",
        a: `Virtual DOM: React maintains a lightweight JavaScript copy of the real DOM (the browser's page structure). When state changes, React updates the Virtual DOM first, then compares it to the previous Virtual DOM, and updates only what changed in the real DOM.

Why this matters: Directly manipulating the real DOM is slow. Every change triggers browser reflow/repaint. React batches and minimizes real DOM updates.

Reconciliation Algorithm (React Fiber):
When state changes, React:
1. Creates a new Virtual DOM tree.
2. Diffs the new tree against the previous one (diffing).
3. Finds the minimum set of changes needed.
4. Applies only those changes to the real DOM (patching).

Key diffing rules:
- Different element types → remove old, create new.
- Same element type → update attributes.
- Lists use key prop for efficient comparison: if items are reordered, React uses keys to match elements. Without keys, React rebuilds the entire list.

Real example from my project:
In my book listing page, when the search filter changes, only the book cards that differ are re-rendered — not the entire page, not the header, not the sidebar. This keeps the UI fast even with 100+ books in the list.

React 18 added startTransition and useDeferredValue to keep UI responsive during heavy re-renders — useful in my admin dashboard where large data tables are filtered in real-time.`

        q: "What is CAP theorem? How does it apply to your distributed systems?",
        a: `CAP Theorem states that a distributed system can guarantee only 2 of these 3 properties simultaneously:

C — Consistency: Every read gets the most recent write (or an error). All nodes see the same data at the same time.

A — Availability: Every request receives a response (not an error), though it may not be the latest data.

P — Partition Tolerance: The system continues operating even when network failures prevent some nodes from communicating.

Since network partitions are INEVITABLE in distributed systems (network cables fail, EC2 instances lose connectivity), P must always be chosen. The real choice is between Consistency and Availability during a network partition.

CP Systems (choose Consistency over Availability):
During network partition, refuse to serve requests rather than return potentially stale data.
Example: Zookeeper, HBase, etcd (Kubernetes' database).
When to choose CP: Financial systems, inventory management — stale data causes real harm.

AP Systems (choose Availability over Consistency):
During network partition, serve requests with potentially stale data.
Example: Cassandra, CouchDB, DynamoDB.
When to choose AP: Social media feeds, recommendation systems — slight staleness is acceptable.

MySQL (CP-leaning): Strong ACID guarantees. I chose consistency for book availability — I'd rather return an error than tell a user a book is available when it's not.

Two common algorithms:

  - Count remaining entries. If > limit → reject.

  - User has a "bucket" of N tokens (N = rate limit).
  - Each request consumes 1 token.
  - Tokens refill at a constant rate (R per second).
  - If bucket empty → reject.
  - Allows short bursts up to bucket capacity.
